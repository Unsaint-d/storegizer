# Storegizer

Домашняя система складского учёта — техническое задание

## Назначение системы

Домашняя система учёта склада, управляемая HID-сканером штрихкодов. Пользователь выполняет складские операции (приём, списание, перемещение предметов), сканируя штрихкоды предметов и ячеек хранения; ввод с клавиатуры/мыши на ПК сведён к минимуму.

Сканирование возможно только через сканер, физически подключённый к серверу (донгл-приёмник воткнут в Linux-хост). Остальные клиенты в домашней сети (включая веб-интерфейс, открытый на самом ПК-сервере) работают в режиме просмотра. В режиме администратора добавляются: просмотр незакоммиченных изменений текущей сессии и возможность редактировать параметры системы (карточки предметов, ячейки и пр.).

Сканер — единственный источник складских операций, подключён только к серверу. Все веб-клиенты в сети (включая браузер на самом сервере) — read-only, плюс расширенные права в admin-режиме (см. выше).

## Технологический стек

**Backend: C.**

- HTTP-сервер: `libmicrohttpd` или `civetweb`.
- WebSocket: `libwebsockets` — нужен для realtime (пуш состояния сессии/буфера в браузер, т.к. сканирование и просмотр могут идти с разных устройств сети).
- БД: SQLite через `sqlite3` C API, режим WAL для более спокойной работы с несколькими читающими клиентами при одном пишущем процессе.
- Перехват сканера: Linux `evdev` (`libevdev`), эксклюзивный grab устройства (`EVIOCGRAB`) по vendor/product ID сканера — это и есть перехват на уровне ОС, независимый от фокуса окна.

**Frontend: React**, раздаётся backend'ом как статика или отдельным сервером в dev-режиме; в проде — один процесс отдаёт и API, и статику React-сборки.

**База данных:** SQLite, файл на диске Linux-хоста.

**Печать:** проект NiimBlue состоит из двух частей — веб-редактора этикеток (`niimblue`) и протокольной библиотеки связи с принтером (`niimbluelib`, TypeScript, MIT). Библиотека работает не только в браузере: у проекта есть готовый Node.js-компонент `niimblue-node` (CLI + REST print-сервер) поверх `niimbluelib`, который умеет печатать через Bluetooth (`noble`) и через USB-serial. Для этой системы печать реализуется именно через `niimblue-node`/`niimbluelib` как отдельный Node.js-процесс на сервере — backend (C) обращается к нему по REST, без браузера и без ручного клика. B1 поддерживает подключение по USB-serial — это надёжнее Bluetooth-пейринга для автоматизации, если принтер физически воткнут в тот же сервер.

**Окружение разработки:** Docker на Windows. Deployment — Linux-хост с реальным USB/HID-доступом.

## Работа сканера

Сканер — стандартное HID-устройство, эмулирующее ввод с клавиатуры: физически это USB-донгл (приёмник), который ОС определяет как обычную клавиатуру и который «печатает» содержимое штрихкода как последовательность нажатий клавиш, завершая скан символом Enter. Никакого специфического драйвера или протокола сверх обычного USB HID Boot Keyboard он не использует — именно поэтому его можно перехватывать через стандартный Linux `evdev`, не отличая программно от настоящей клавиатуры, кроме как по vendor/product ID устройства.

**Будущее развёртывание на Orange Pi.** Чтение сканера через `evdev` не привязано к архитектуре x86 — это обычный Linux-механизм чтения `/dev/input/eventX`, который одинаково работает на любом SBC с Linux (Armbian/Ubuntu на Orange Pi в том числе), при условии что:

- в ядре включён и загружен модуль `usbhid` (стандартно включён в большинстве сборок Armbian/Ubuntu для Orange Pi);
- у конкретной модели Orange Pi есть полноценный USB-хост порт (USB-A), а не только USB-OTG — на некоторых компактных моделях единственный USB-порт работает в режиме OTG и требует OTG-хаба для подключения обычных USB-устройств; это нужно проверить под конкретную модель платы до покупки/переноса;
- у процесса backend есть права на чтение нужного `/dev/input/eventX` — потребуется udev-правило, дающее доступ по vendor/product ID сканера, без запуска сервиса от root.

С этими оговорками чтение сканера на Orange Pi принципиально не отличается от чтения на обычном Linux-хосте.

## Модель данных (концептуально)

- **Предметы** — модель «тип + количество», без учёта по уникальным серийным экземплярам.
- **Ячейки** — два вида: mono (жёстко привязана к одному типу предмета) и poly (хранит разные типы).
- **Сессии** — несохранённые изменения копятся в буфере, коммитятся в основную БД по завершении сессии; до коммита возможен ручной откат.
- **Аудит-лог** — отдельная неизменяемая история всех совершённых (закоммиченных) операций: что, сколько, когда, в какую/из какой ячейки.

Грамматика сканирования (порядок сканов, таймауты, привязка mono-ячеек, упаковки/вложенные предметы, модель сессий) зафиксирована отдельно в [docs/scanning-grammar.md](docs/scanning-grammar.md), вместе со схемами. Там же — оставшиеся нерешённые детали грамматики (STOP_CUR_OP, разворачивание упаковки при удалении и т.п.), см. раздел «Открытые вопросы» в этом документе.

## Открытые вопросы, которые нужно решить в процессе реализации

1. **Docker на Windows vs evdev на Linux.** Контейнер на Windows не имеет доступа к реальным Linux input-устройствам — backend уже умеет работать без реального сканера (см. `SCANNER_DEVICE`/`POST /api/debug/scan` в [backend/src/main.c](backend/src/main.c)), для дев-окружения этого достаточно; перехват через `evdev` по-прежнему нужно тестировать на реальном Linux-хосте.
2. ~~**Формат и симвология штрихкодов**~~ — решено: префиксная схема (`STG-BIN-…`/`STG-SVC-…`/всё остальное — предмет), см. [docs/scanning-grammar.md](docs/scanning-grammar.md#1-классификация-кода-при-сканировании).
3. **Аутентификация в сети.** Доступ открыт на всю домашнюю сеть — нужно решить, достаточно ли доверенной сети или нужна базовая авторизация. Частично сузилось: открытие «сессии работы» (см. документ по грамматике) уже требует admin-аутентификации, но сама схема аутентификации ещё не спроектирована.
4. **`niimblue-node` как компаньон-сервис.** Проект в статусе Alpha, API может меняться — нужно зафиксировать конкретную версию. Также нужно решить транспорт до принтера: USB-serial (надёжнее, если B1 физически рядом с сервером) или Bluetooth через `noble` (нужны системные зависимости и права на BT-адаптер).
5. **Параллельный доступ к SQLite с нескольких сетевых клиентов** — WAL смягчает проблему, но при росте нагрузки может понадобиться единая точка записи внутри backend-процесса (очередь операций).
